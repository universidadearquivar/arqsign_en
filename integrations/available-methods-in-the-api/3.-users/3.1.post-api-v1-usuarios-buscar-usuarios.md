# ✔️ 3.1.POST/api/v1/usuarios/buscar-usuarios

## Request

**Guidelines:**

When the required field is marked as "Yes" = Always required

When the required field is marked as "No" = Optional information

When the required field is marked as "Maybe" = It will be required in some cases. To know these cases, please refer to the description of the specific validation topic.

## Validations

### Specific Validations

**ativos**

> **Description:** Parameter indicating whether to retrieve only active users or not.
>
> **Format:** Bit: 1 - True, 0 - False
>
> **Required:** <mark style="color:red;">Yes, if the "usuarios" object does not contain a user ID.</mark>
>
> **Validation:**
>
> a. If the **value is 1 (true)**, the system will **return only active users of the account**, sorted alphabetically by name.
>
> b. When the **value 0 - false is sent or not sent**, the system **returns all users of the account (active, blocked, inactive)**, sorted alphabetically by name.
>
> c. The "**active**" parameter is mandatory when no user IDs are provided in the "**usuarios**" object.
>
> d. If a user ID is provided in the "**usuarios**" object, the system disregards the "**active**" **parameter** and returns the data of the specified users, sorted alphabetically by name.

**usuarios**

> **Description:** It is optional to provide user IDs for querying.
>
> If the user does **not provide user IDs in the JSON**, the system r**eturns all users of the account**, according to the **active parameter**, sorted alphabetically.
>
> If the user **provides one or more user IDs in the JSON**, the system **returns the data of the specified users,** sorted alphabetically.
>
> **Format:** Guid
>
> **Required:** <mark style="color:blue;">No</mark>
>
> **Validation:**
>
> a- When a user ID is provided, the system validates if the user ID belongs to the account.
>
> **Note:** If at least one user belongs to the account, the system returns the data of that user.

### General Validations

1. The user must provide the AppKey of the account for which user data is being requested.
2. Only accounts with an "Active" status can retrieve user data via the ArqSign API.

## Return Validations

### Error: 400 - Bad Request

This error occurs when the request cannot be interpreted and/or the server attempts to process it but one or more parameters are invalid, such as improperly formatted resources or missing data.

Details: The response body contains a code and error message.

**a. Mandatory Item**: This message is displayed in singular or plural when one or more mandatory items have not been sent in the API call.

> **Message:** "The following item(s) are required: 'list of item names separated by commas.'"

**b. Incorrect format:** This message is displayed in singular or plural when one or more items have been sent in an incorrect format.

> **Message:** The listed item(s) have the incorrect format: “item names separated by commas.”

**c. Non-existent Ids**: This message is displayed in singular or plural when one or more Ids sent do not exist.

> **Message:** The listed id(s) do not exist: “names of the items that are table Ids, separated by commas”.

**d. Some parameter is incorrect or non-existent**: This message is displayed when the call is made with a parameter written incorrectly or when an information that does not exist in the method is sent.

> **Message:** Some parameter is incorrect or non-existent.

### Error: 401 - Unauthorized

This error occurs when:

* The API key is incorrect or not provided properly.
* The account status is not "Active."

### Error: 404 - Not Found

This error occurs when the requested resource or endpoint cannot be located.

### Error: 500 - Server Error

This error occurs due to:

* Internal server errors.
* Failures in the ArqSign platform.
* Incorrect parameter formats.
* Improper JSON formatting.

## Successful Return

Status 200 - Success

If **no user IDs are provided in the JSON**, the system **will return all users of the account**, sorted alphabetically by name, based on the "**active**" parameter:

* If **"active" is 1 (true)**, only **active users are returned**.
* If **"active" is 0 (false) or not provided**, **users with all statuses (active, blocked, inactive)** are returned.

**If user IDs** are provided in the JSON, the system **will return data for the specified users**, sorted alphabetically by name.

<figure><img src="../../../.gitbook/assets/image (1).png" alt=""><figcaption></figcaption></figure>

### User Data

**1- id**

The system returns the user's ID.

**2- nome**

The system returns the user's full name.

**3- status**

The system returns the user's account status as follows:

* Active
* Inactive
* Blocked

**4- remetente**\
The system returns whether the user is a document sender or not.

* Users with permission to send processes **(Send Document for Signing).**
